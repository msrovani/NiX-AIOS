# HUD no QEMU — porque o `jarbas-cage` estava inactivo e a prova visual

**Data:** 2026-11-08 · **ISO:** `iso-hw` de `main` (sha `dbe9d0e5…`, 7 050 903 552 B)
**Estado:** QEMU/TCG **OBSERVED** (lab, `≠ metal` ADR-0113). Aceleração de GPU **NOT-TESTED**.

Pergunta: porque é que o `jarbas-cage` ficou `inactive` no QEMU da prova de
inferência, e dá para ver o HUD ali?

## Resposta curta

**Não era a GPU.** O unit tem `unitConfig.ConditionPathExists =
"/var/lib/nosd/gui-start"` (`modules/jarbas-cage.nix`) e o marcador não existia —
o `jarbas-cage` só arranca depois do questionário Q1–Q5 (hotswap) ou do
persist-check do 2.º boot, e neste guest com auto-login em `ttyS0` esse fluxo
nunca correu. O systemd saltou o unit **sem escrever uma linha**.

Com o marcador criado à mão (o que o hotswap faz), o cage subiu e o HUD
renderizou — ver `docs/evidence/artifacts/hud_qemu_cage.png`.

## Prova do diagnóstico (guest, série em socket)

Antes do marcador:

```
○ jarbas-cage.service - JARBAS kiosk (cinematic / iGPU cage)
     Loaded: loaded (/etc/systemd/system/jarbas-cage.service; linked; preset: ignored)
     Active: inactive (dead)

journalctl -b -u jarbas-cage --no-pager | tail -30
-- No entries --
```

```
ls /var/lib/nosd/gui-start /var/lib/nosd/firstboot.done /var/lib/nosd/aios-mode
  -> os três: "Arquivo ou diretório inexistente"
seatd.service -> active (running)          (o seat estava bom)
ls -l /dev/dri -> card0, card1, renderD128 (virtio_gpu carregado)
```

Ou seja: seatd activo, DRM presente, e ainda assim `inactive` — porque a
condição falhou. Nada de "faltou GPU".

Depois de `sudo -n touch /var/lib/nosd/gui-start; sudo -n systemctl start jarbas-cage`:

```
act=active
nov 08 17:27:18 nixaios systemd[1]: Starting JARBAS kiosk (cinematic / iGPU cage)...
nov 08 17:27:19 nixaios systemd[1]: Started JARBAS kiosk (cinematic / iGPU cage).
```

## Caminho de render dentro do guest

Do `/var/lib/nosd/jarbas-cage.log`:

```
[ERROR] [render/egl.c:334] Software rendering detected, please use the WLR_RENDERER_ALLOW_SOFTWARE environment variable to proceed
[ERROR] [render/egl.c:611] Failed to initialize EGL context
[ERROR] [render/vulkan/renderer.c:2608/265] Could not match drm and vulkan device / Could not retrieve physical devices: ERROR_INITIALIZATION_FAILED (-3)
[INFO] [render/pixman/renderer.c:328] Creating pixman renderer
[INFO] [backend/drm/drm.c:270] Found 1 DRM planes
[INFO] [backend/drm/drm.c:1861] 'Virtual-1' connected
[INFO] [backend/drm/drm.c:1670]   1280x800 @ 74.994 Hz (preferred)
```

Com `virtio-gpu` não há EGL/GLES utilizável nem Vulkan: o wlroots cai para
**pixman** (CPU) e desenha no conector `Virtual-1`. Sem GPU o cage desenha, só
não acelera — que é exactamente o que o fallback do módulo prevê.

## Como repetir (e duas armadilhas)

```bash
qemu-system-x86_64 -cpu qemu64 -m 4G -smp 4 -cdrom <iso> -boot d \
  -netdev user,id=net0 -device virtio-net-pci,netdev=net0 \
  -device virtio-gpu-pci -vnc 127.0.0.1:1 \
  -serial unix:$HOME/ser.sock,server,nowait \
  -monitor unix:$HOME/mon.sock,server,nowait
# no guest (auto-login nixos, sudo sem password):
#   sudo -n touch /var/lib/nosd/gui-start && sudo -n systemctl start jarbas-cage
# captura: monitor -> screendump /home/msrov/shot.ppm  (P6 -> PNG)
```

1. **A série aceita um cliente.** Depois de um cliente desconectar, o segundo
   `connect` dá `Transport endpoint is not connected` e os comandos são ecoados
   sem executar. Um único cliente que faz tudo (marcador + start + diagnóstico)
   é a forma que funciona.
2. **`quit` no monitor fecha a VM.** O cliente de captura mandava `screendump`
   e depois `quit`; a primeira captura saiu e a segunda nunca existiu porque o
   QEMU já tinha saído.

## O que NÃO fica provado

- **Aceleração de GPU**: pixman/software. `nvidia-smi AUSENTE` no próprio HUD.
- **MIC/CAM**: `MIC OFF`, `CAM OFF`; o greeting caiu para espeak
  (`jarbas: piper greeting FAILED/timeout — fallback espeak`) e não há placa de
  som no QEMU.
- **S2/CUDA**: `S2/PRO ausente`, `8082 · S2 N/A` — é o esperado sem NVIDIA.
- **Quem desenha**: o probe terminou antes de `pgrep -af 'cage|chromium|nos-jarbas'`;
  a captura prova o resultado, não o processo (o HUD é o ORB web).
- **Metal**: nada disto substitui o Core 7/i5.
