# Evidence — M8.1 anti-entropy por delta (version vector)

**Data:** 2026-10-27  
**Estado:** implementado e provado (`mesh-2vm-crdt` PASS com delta).  
**Fase:** M8.1 (fatia 1 — delta por VV; bloom e nsgdb ficam para M8.1b).

## O que mudou

| Antes (M8) | Agora (M8.1) |
|---|---|
| `crdt.sync` enviava o **store completo** | envia só o **delta** que o peer não tem |
| sem VV de estado | `CrdtStore::version_vector()` (max por peer) |
| — | `CrdtStore::delta_since(&vv)` |
| 1 troca | **2 trocas**: pull (envia só `vv`) + push (envia o delta desde o `vv` do peer) |

Wire interno (cifrado pelo Noise do M6.1):
```json
{ "vv": { "node": 3 }, "entries": [ ... ] }
```
O servidor funde `entries`, calcula `delta_since(vv)` e devolve
`{ vv: local, entries: delta }`.

## Provas

| Teste | Resultado |
|---|---|
| `cargo test --workspace` | verde (36 + 14 + …) |
| `mesh-2vm-crdt` (2 VMs, canal Noise) | **PASS** — A→B leva `k1`, B→A leva **só** `k2`, ambos com 2 entradas |
| `clippy -D warnings`, `fmt --check` | ok |

O teste é o que distingue M8 de M8.1: a segunda sincronização **não** reenvia
`k1` (o `vv` do peer já diz que ele o tem).

## Honestidade / residual

- **Sem bloom filter** ainda: o pull manda só o `vv`, mas o push calcula o
  delta local (custo O(n) no nó que envia). Bloom/Merkle reduzem o caso
  "peer tem quase tudo" — fica para M8.1b.
- **Sem persistência**: o log de ops continua em memória; um restart perde o
  estado. `nsgdb` como log append-only é o próximo passo (durabilidade/replay).
- **Sem compactação** de tombstones/versões antigas.
- A confiança continua a ser "peer com chave fixada" (M6), canal cifrado (M6.1).
